# GDB pretty printers

`structo` ships GDB pretty printers for its `structo::sync` primitives, so
`print`/`display` show readable, decoded lock state (`structo::sync::
rw_spin_lock [write-locked by owner=0x...]`) instead of raw struct dumps
of internal `state_`/`owner_`/bit-packed fields.

This follows the exact same approach as `reloco`'s own GDB pretty printers
(see that project's `docs/gdb-pretty-printers.md`) -- same three delivery
mechanisms, same embedded-header generation script, same testbed
structure -- applied to `structo::sync` instead of `reloco`'s containers.

The printers live in one place, `tools/gdb/structo_printers.py`, and are
usable in three interchangeable ways.

## 1. Source it directly in a running GDB session

```
(gdb) source /path/to/structo/tools/gdb/structo_printers.py
```

Useful for a one-off debugging session without touching the target binary
or your GDB configuration.

## 2. Auto-load it for a specific binary

Place a `<binary>-gdb.py` file next to your executable (or anywhere on
GDB's auto-load path) containing:

```python
import sys
sys.path.insert(0, "/path/to/structo/tools/gdb")
import structo_printers
structo_printers.register_structo_printers()
```

GDB loads this automatically whenever it loads a matching binary (subject
to `auto-load safe-path`, see below).

## 3. Embed it directly into the binary (no external files)

```cpp
#include <structo/sync/gdb_printers.hpp>
```

Including this header anywhere in your program (typically once, from the
translation unit containing `main`) embeds the *entire* contents of
`tools/gdb/structo_printers.py` into a `.debug_gdb_scripts` ELF/COFF
section via inline assembly, using GDB's ["Python text" section-script
mechanism](https://sourceware.org/gdb/onlinedocs/gdb/dotdebug_005fgdb_005fscripts-section.html).
When GDB loads the resulting binary, it automatically extracts and runs
that exact script, registering the printers -- no `source` command, no
`<binary>-gdb.py` file, and no `sys.path` setup required on the machine
doing the debugging. This is the recommended option for shipping printers
alongside a distributable binary or a project's own test executables --
especially relevant for `structo`, whose consumers are typically kernel/
hypervisor images debugged over a remote `gdb` stub rather than run
locally.

This header is opt-in only: it is not included by any other `structo`
header and adds no cost unless you explicitly `#include` it. It is also
deliberately excluded from automated cross-compiler testing/CI: the
`.debug_gdb_scripts` embedding relies on GNU-assembler inline `asm` syntax
that has no equivalent on MSVC (or other compilers without GNU inline-asm
support), so the header guards its body on `defined(__clang__) ||
defined(__GNUC__)` and is a silent no-op elsewhere -- there is nothing
portable to verify by including it by default.

`include/structo/sync/gdb_printers.hpp` is generated by
`tools/gdb/generate_embedded_header.py` from `structo_printers.py` and
should never be hand-edited; regenerate it after changing the printer
script:

```
python3 tools/gdb/generate_embedded_header.py
```

## `auto-load safe-path`

Both option 2 and option 3 are subject to GDB's `auto-load safe-path`
security setting, which by default only trusts scripts from a small set of
system locations. If GDB declines to load the printers, either add the
binary's directory:

```
(gdb) add-auto-load-safe-path /path/to/binary/dir
```

or add it permanently to `~/.gdbinit`. See the [Auto-loading safe
path](https://sourceware.org/gdb/onlinedocs/gdb/Auto_002dloading-safe-path.html)
section of the GDB manual for details.

## Coverage

Printers are registered for every `structo::sync` primitive built so far:
`kernel_spin_lock`, `ticket_spin_lock`, `queue_spin_lock` (and its nested
`node`), `rw_spin_lock`, `queue_rw_spin_lock` (showing the decoded
writer/reader/waiting state and its inner `writer_queue_`), `backoff`,
`softlock_detector`, `preemption_guard`, `irq_guard`, `spinlock_entry_guard`,
and `core_pin_guard`.

The lock printers decode the packed atomic state words rather than
dumping raw integers: `kernel_spin_lock`/`ticket_spin_lock`/
`queue_spin_lock` show `[unlocked]` or `[locked by owner=0x...]` (plus
ticket/queue-specific detail); `rw_spin_lock`/`queue_rw_spin_lock` decode
the `writer_bit`/`writer_waiting_bit`/`reader_mask` state word into
`[write-locked by owner=0x...]`, `[read-locked by N reader(s)]`, or
`[unlocked]`, with a `, writer waiting` suffix when applicable. The RAII
guards (`preemption_guard`, `irq_guard`, `spinlock_entry_guard`,
`core_pin_guard`) show only `[armed]`/`[disarmed]` (plus any
guard-specific captured state, e.g. `irq_guard`'s saved flags or
`core_pin_guard`'s pinned CPU) since that's the entirety of their
observable state.

Every printer reads the underlying `std::atomic<T>` fields by
reinterpreting their raw memory as a same-width plain integer (see
`_read_atomic` in `structo_printers.py`) rather than indexing any
particular standard library's internal field names -- this works
unmodified across libstdc++'s several internal `atomic<T>` layouts and
libc++'s, since every mainstream implementation places a lock-free
`atomic<T>`'s bytes with no leading padding.

## Regenerating and testing

After editing `tools/gdb/structo_printers.py`:

1. Regenerate the embedded header: `python3 tools/gdb/generate_embedded_header.py`.
2. Add or update a test case for the changed/new type in
   `tools/gdb/testbed/` and run `tools/gdb/testbed/run.sh`, which compiles a
   real program using the printers and checks their output under GDB in
   all three loading modes above. See `tools/gdb/testbed/README.md` for
   how to add a case; that testbed is not part of the main build/CI, so it
   must be run explicitly.
